What is HR4E Studio?

HR4E Studio is the web-based environment for working with HR4E vaults. It provides a unified place to view, edit, extract, and eventually analyze vault contents. Studio is designed to operate offline-first, but not offline-only, allowing clinicians and patients to work with vaults even when connectivity is limited while still supporting synchronization when available.

The current Studio implementation is an alpha version intended for early testers. It is functional but not yet modular, and it focuses on demonstrating the viability of a portable, browser-based environment for HR4E workflows.

Current Capabilities (Alpha)

The alpha version includes two tightly coupled components:

  • Editor/Viewer — a basic interface for viewing and editing CCD-subset documents stored in vaults.
  • Extractor/Loader — a deterministic tool for generating vault contents from structured inputs. This prototype demonstrates how vaults can be populated without requiring direct access to an EHR.

These components are implemented together in a single-page application. This design is suitable for prototyping but will be replaced by a modular architecture as Studio matures.

Relationship to the Foundation Layer

Studio corresponds to the “configurable web-based environment” described in the HR4E Foundation Layer. It is the primary interface through which clinicians, students, and franchisees interact with vaults. Over time, Studio will integrate additional tools — Analyzer/Reporter, Biller/Bookkeeper, and modular Extractor/Loader profiles — providing a single interface for working with vaults across clinics, schools, and patient-carried eHP workflows.

Authentication & Security (Alpha)

The alpha version of Studio uses Microsoft identity and OneDrive for authentication and storage. This approach was chosen because it provides secure, standards-based authentication without requiring HR4E to operate its own identity provider or maintain user credentials.

Studio is registered as an application in Azure Active Directory. Users authenticate using the Microsoft Authentication Library (MSAL), which handles OAuth2 and OpenID Connect flows directly in the browser. After authentication, Studio receives an access token that allows it to read and write files in the user’s OneDrive.

This architecture provides several advantages:

  • No HR4E-managed credentials — authentication is handled entirely by Microsoft identity.
  • Secure storage — vaults stored in OneDrive benefit from Microsoft’s encryption-at-rest and secure sync infrastructure.
  • Browser-only operation — MSAL enables authentication without requiring a backend server, consistent with HR4E’s offline-first design.
  • Easy local development — developers can run Studio locally and still authenticate using their Microsoft account.

As Studio evolves, authentication will remain modular. Future versions may support local-only vaults, USB-based eHP workflows, and optional cloud synchronization using OneDrive or other providers.

Future Roadmap

  • Modular tool architecture (Editor, Extractor, Reporter, Biller as independent modules)
  • Offline-first synchronization workflows for eHP and clinic vaults
  • Configurable Extractor/Loader profiles for different EHR systems
  • Support for encounter summaries, immunization tracking, and school health workflows
  • Expanded authentication options (local-only, USB-only, optional cloud sync)
  • Improved OneDrive integration for multi-vault management

Running this version of Studio Locally

The repository README contains full developer instructions. If the README looks adequate, the steps below summarize what a WebStorm-capable developer needs to do to clone and run the alpha:

  • Clone the repo — `git clone https://github.com/hr4e-revisited/studio-web.git` and open the project in WebStorm.
  • Install dependencies — run `npm install` (the project uses a lightweight dev server and MSAL client libraries).
  • Copy auth template — duplicate `authConfig.example.js` to `authConfig.js` and fill in the Azure app values (clientId, authority, redirectUri). Do not commit secrets.
  • Start the dev server — run `npm run dev` (or use WebStorm’s npm runner). Studio will be available at `http://localhost:5173/` (or the port shown by the dev server).
  • Authenticate — sign in with a Microsoft account via the MSAL popup; Studio will request OneDrive access and receive an access token for file operations.
  • Create or point to a vault — create a vault folder in your OneDrive or use the Studio UI to create one; the app reads/writes CCD-subset documents there.
  • Notes for developers — the alpha is a single-page prototype (Editor/Viewer + Extractor/Loader). Expect tight coupling; modularization is planned for future releases.

Exporting your electronic health record as a collection of CCDs from Epic at your organization

It's fine to hand‑enter HR4E‑ccdsubset data manually from the Editor/Viewer, but that can get tiresome. Alternatively, you may be able to upload your personal health data from a standard Epic EHR extract. How do you generate that extract? Below are practical steps (based on the Sutter Health / MyChart flow) that produce a ZIP containing CCD XML files you can point the Extractor/Loader at for experimentation. Many Epic sites provide an analogous export; if you cannot find these options in your portal, contact your medical records office and request a CCD/CCDA export.

Disclaimer: experience with the deterministic HR4E Exporter/Loader is VERY limited. This has been tried with a small number of visits at Sutter Health, but this may or may not work for you, and may or may not work at the organization that manages your health record.

  1. Sign in to MyChart — Login to MyChart for the organization that maintains your health record in Epic.
  2. Open the Sharing Hub — Navigate to the area of the portal labeled something like Sharing Hub (or a similarly named section for sharing or exporting records).
  3. Start the export — Find and click Download health and visit summary.
  4. Choose visits — On the export page you should see three tabs: Single Visit, Date Range, and All Visits. Select the tab and date range that will include roughly 10–20 visits (or the set you want), then click Continue.
  5. Preview and request the export — You will arrive at a Preview documents page. Click Download All to request the export.
  6. Wait for the ZIP and locate the CCDs — The portal may take some time (sometimes up to 24 hours) to prepare the export. When ready you will receive a ZIP file. Inside the ZIP you will find files named like DOC0001.xml, DOC0002.xml, etc. Those XML files are the CCD/CCDA documents. Unzip the archive and point the Extractor/Loader at the top-level directory created by the unzip operation; the loader will discover the CCD XML files and process them.
  7. (Optional) View the CCDs in Safari — On macOS, Apple’s Safari can be pointed at the unzipped XML files and will often render them using the accompanying stylesheets included in the export. This provides a quick human-readable preview of each CCD without additional tools. Note that other commercial browsers typically do not apply the same stylesheets automatically.

After unzipping, the Extractor/Loader should be pointed at the highest-level directory produced by the unzip operation. The loader will recursively discover CCD XML files (DOC0001.xml, DOC0002.xml, …) and convert them into the HR4E-ccdsubset format for use in Studio. If you encounter files that are not recognized, check that the export contains standard CCD/CCDA XML documents and that the files are not encrypted or wrapped in a proprietary container.

If your portal does not offer a CCD/CCDA export, contact the medical records office and request a standard CCD/CCDA extract for personal use; most Epic-based organizations can provide this on request.
