What is an HR4E vault?

An HR4E vault is a file‑system directory that contains a collection of HR4E CCD‑subset documents, along with optional indexing metadata stored in a SQLite database. Vaults are the core portable artifact of HR4E: they can be carried by patients, aggregated by clinics, synchronized across encounters, and processed by HR4E tools such as the Editor/Viewer and Extractor/Loader.

Vault contents

Each vault contains:

  • A set of HR4E CCD‑subset documents, each representing a clinical encounter, screening, immunization record, lab result, or other structured clinical artifact.
  • An optional vault-index.sqlite file that stores metadata extracted from each document, enabling fast lookup, filtering, and aggregation.
  • A simple mechanism for regenerating vault-index.sqlite at any time by scanning the vault directory and reading metadata from each CCD‑subset document.

The specification and definition of HR4E CCD‑subset documents is maintained in the hr4e-revisited/hr4e-ccdsubset repository.

File naming convention

HR4E vaults use a strict naming convention that supports workflow automation while avoiding exposure of protected health information (PHI). Each document filename follows the pattern: 

dd-yyyymmdd-UUID

where:

  • dd — a two‑letter code for the CCD document type (CS, CN, IR, LR).
  • yyyymmdd — the date associated with the document.
  • UUID — a unique identifier generated by HR4E tools.

Examples derived from the sample non‑PHI vault:

  • CS-20240615-3fa85f64-5717-4562-b3fc-2c963f66afa6.xml
  • CN-20240615-9b2c4d10-1e3f-4a2b-8c9d-0f1a2b3c4d5e.xml
  • IR-20240616-7e57d004-2b97-0e7a-b45f-5387367791cd.xml
  • LR-20240617-4c8a331e-2f44-4b9f-bc3a-1d2e3f4a5b6c.xml

The full filename serves as a key in vault-index.sqlite, but does not reveal PHI. All PHI resides inside the CCD‑subset documents and in the SQLite index, not in the filenames.

Sample (non‑PHI) Vault

A complete non‑PHI demonstration vault is available in the HR4E CCD‑subset repository:

hr4e-revisited/hr4e-ccdsubset/vault-spec/HR4E-demo-A

This sample vault illustrates:

  • The directory structure of an HR4E vault
  • Multiple CCD‑subset documents using the HR4E naming convention
  • A corresponding vault-index.sqlite file
  • How HR4E tools read, display, and aggregate vault contents

Developers can use this sample vault to test HR4E tools, validate workflows, and understand how vaults behave across different deployment scenarios.

PHI considerations and security

Although vault filenames are PHI‑safe, the vault contents themselves are not. Each CCD‑subset document contains clinical information, and the SQLite index contains metadata derived from those documents. For this reason, users must ensure that vaults are stored and transmitted securely.

Importantly, PHI security is not a property of the vault format itself. Instead, it is a property of how vaults are handled, stored, encrypted, and accessed by HR4E tools and by users.

Encryption and lifecycle management

HR4E vaults will be encrypted whenever they are stored between uses. This applies both to:

  • Personal vaults carried by patients between clinical encounters, known as HR4E electronic health passports (eHPs).
  • Aggregated vaults collected by clinics to document services rendered during a day or event.

Modern mobile devices provide strong biometric authentication, and HR4E apps will leverage these capabilities to secure vault contents throughout their lifecycle. The precise sequencing of vault encryption and decryption is currently under active development as HR4E tools evolve.
